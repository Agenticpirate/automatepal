# Preview hardening evidence

2026-10-28. Security/reliability work, not enterprise certification or production acceptance.

## Run locally

- `npm run test:hardening`: bounded 6/min guard, window expiry, max 5000 identities fail-closed, auth outage injection, no third-party load.
- `DATABASE_PASSWORD_FILE=<private file> npx tsx scripts/verify-hardening-db.ts`: two synthetic auth principals under actual authenticated/anon SQL roles; all fixtures roll back. 15 table cross-tenant reads, foreign RPC mutations, forged case/audit inserts, inaccessible webhook signing secret, capability denial, own-data deletion and foreign-data survival. Most tables use zero-row cross-tenant checks; populated end-to-end independent second-browser tests remain required.
- `node scripts/verify-hardening-pages.mjs`: local mobile controls/headers, 10 concurrent local liveness reads, five unauthenticated route denials. Not a capacity benchmark.
- `npm audit`: full dependencies, 0 known advisories at this checkpoint. A scan is not proof of no vulnerabilities.
- Existing safety, widget, billing, webhook and rollback DB suites retain their scope.

## Controls and limits

Owner writes are recorded by DB triggers as IDs, resource type, operation and time only. Last 1000 events per workspace; no raw source/question text, contact, URL, bearer token or webhook key. This is not tamper-proof compliance logging. Knowledge answer failures emit fixed-vocabulary stage logs without input or identity.

Preview-data deletion requires exact typed words, checks ownership through auth.uid(), serializes with knowledge operations and refuses uncertain/executing action records. It deletes preview application data and revokes all demo/read-only capabilities by removal. It does not cancel/refund payments, delete the Supabase Auth identity, provider-held information, external copies or backups. Do not erase unresolved payment records. No automated age purge exists. Account deletion remains manual as the privacy notice states.

Retention for owner replies (045): `support_messages` rows cascade with their case, are visible to the visitor only while the case link is unexpired, are capped at 100 per case, and are removed by preview-data deletion before `support_cases`. Ticket history stores only "Owner replied in the widget", never the reply text. Visitor polling is limited to 15 requests per minute per case link in-process. Nothing is emailed.

Headers include nosniff, no-referrer, HSTS, Permissions-Policy disabling camera/mic/geolocation/payment, and a limited CSP restricting objects/base/form actions. Full script-src CSP is not claimed. Frame restrictions are intentionally absent for the opt-in widget. Response caches are disabled on private API/demo surfaces. Authentication fetch exceptions fail closed; outage may appear as sign-in required rather than a precise dependency diagnosis.

MCP server (`/mcp`, 046): the bearer must be an `ap_ro_` token of the right shape before any database call (else 401 with `WWW-Authenticate`); a browser `Origin` must be this app (else 403); POST only; 64 KB body cap; one JSON-RPC message per request (no batches); 30 requests per minute per token in-process. The token hash is checked in the database on every request (revoked or expired gives 401) and again inside every tool RPC together with the scope-to-tool map, so an unregistered tool cannot be reached another way. Tools return metadata and counts, except `get_unanswered_digest`, which includes visitor question text (grouped, last 7 days). No tool returns owner or visitor message bodies, contact addresses, source text, ciphertext, proof hashes, key hints or account labels; the encryption key label becomes a needs-rotation flag server-side. The two write tools cannot publish anything or contact anyone: proposals are stored unpublished with `pending_approval`, a trigger refuses publishing while pending, approval needs the manager role, and test questions record no interactions. Daily caps (10 proposals, 20 test questions per workspace per UTC day) are counted in `mcp_calls`, whose 500-row pruning never removes the current day's counted rows. `mcp_calls` keeps tool name and outcome only (never arguments), is readable by admins and is removed by preview-data deletion. Errors shown to clients are fixed messages; database errors do not pass through.

MCP write tools (047): each needs its own new scope (`conversations:reply`, `settings:read`, `settings:write`); `mcp_tool_allowed` and `mcp_token_scope` were extended without granting anything to the six existing scopes, and every tool RPC re-checks the token and scope. `mcp_reply_to_conversation` refuses unless the case belongs to the token's workspace, is already taken over and its link is unexpired, and has fewer than 100 messages; it never changes the inbox state. The ticket event says a reply was sent via an MCP token, never the text; the message row stores the token id and the workspace owner as actor; an owner audit row is written. `mcp_update_settings` accepts only `visitorChoice`, `hideContact` and `workingHours` (validated in SQL: types, known time zone, up to 14 HH:MM ranges, 300-character away message), merges only those keys into the controls (branding, origins and paths are untouched), is capped at 20 per workspace per UTC day (counted rows survive call-log pruning) and is audited. The server validates the merged result with the Widget studio zod schemas before calling it.

Visitor chat: a deterministic prompt-injection guard (`lib/prompt-guard.ts`) refuses embedded system prompts, pasted transcripts and requests to ignore the instructions, in the widget and again in `/api/support` before the rate limit, question budget or any model call. Every model call appends an instruction-privacy rule. Leads (`/leads`): manager role and up in the API; `delete_lead` checks the role and acting workspace in the database; CSV cells are formula-escaped. Widget SDK events carry no personal data; the panel posts only to the embedding origin and `widget.js` accepts messages only from its own frame at the app origin.
## Recovery and free-tier limits

- Supabase docs recommend free-tier projects export via CLI db dump and keep off-site copies. Managed daily backups are Pro/Team/Enterprise, not assumed on free tier: https://supabase.com/docs/guides/platform/backups
- Render docs say free services are not for production, sleep after 15 minutes and can restart. No persistent disk/scaling. Usage overages can bill when a payment method exists; no upgrade or payment method has been added by this work: https://render.com/docs/free
- Git contains additive schema migrations and application code. This is not a data backup.
- An encrypted off-site backup destination/retention policy and isolated restore target are not established. No dump, restore, RPO or RTO success is claimed. Do not restore into the active preview. Before real data: approve destination, take a compatible logical dump, restore only into an isolated DB and verify schema/RLS/counts/capability revocation without logging row content.
- No keep-alive ping, third-party hammer test, always-on worker or spend was introduced.

## Billing support (044, built locally)
- Read-only in code: `guardedRequest` (`lib/billing/core/http.ts`) matches method, path template and query keys against each provider's allowlist before `fetch`; anything else throws `write_blocked`. Every contract test probes POST/PUT/PATCH/DELETE and confirms zero fetches. Payment execution stays OFF; refunds are owner review records only.
- Credentials: AES-256-GCM, random 12-byte IV, AAD bound to workspace, provider and mode, versioned blob with key id. Keyring `BILLING_ENCRYPTION_KEYS` plus `BILLING_ENCRYPTION_ACTIVE_KID`; rotation re-encrypts and the owner view flags rows on an old key. The ciphertext and proof-hash columns are never granted to signed-in clients; RPCs that read or write billing data need a server proof derived from `BILLING_RPC_SECRET` (visitor reserve/finish included). Disconnect deletes the ciphertext row and keeps a metadata event. These env values are not set on this machine yet, so connections cannot be saved until they are.
- Outbound: 10 s timeout, no redirects, 1 MB body cap, one jittered retry on network/5xx only, Retry-After honoured on 429 with a per-connection cooldown, circuit breaker after 5 failures for 60 s, 10 requests per 10 s per connection, 60 s lookup cache keyed by connection, verification and intent so it never crosses customers.
- Limits before any provider call (DB): 60 lookups per 10 minutes and 300 per UTC day per workspace, 30 per 10 minutes per provider, 5 failed verifications and 30 lookups per case.
- Customer scope: order/invoice/payment id plus payment email, compared as sha256 digests in constant time and never stored or logged; not-found and mismatch return the same message; the sealed scope lasts 30 minutes (capped at case expiry) and every returned record is re-checked against it.
- Redaction: provider keys, Bearer/Basic values, emails and long tokens are masked in every billing error, log and live-check line; provider response bodies never enter error messages.
- Audit: one metadata row per lookup (provider, mode, intent, outcome, redacted record id, status, amount, currency, time) plus an owner audit event; no email, name, card data or reference text. Preview-data deletion removes connections, events, lookups and verifications.
- Evidence: `npm run test:billing-support` (crypto, redaction, HTTP guard, ten provider contracts, isolation) and `verify-billing-db` (62 checks, local Supabase). Real-provider behaviour is verified only for the PayPal sandbox; the other providers are contract/mock tested.
